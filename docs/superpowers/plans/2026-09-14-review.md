## Findings

### P1 — Preserve surrogate pairs across uploaded state chunks

Location: `src/storage/remote-store.ts:66–67`.

The upload slices serialized JSON every 60,000 UTF-16 code units. An astral character (including supplementary Japanese characters and emoji) crossing that boundary becomes two lone surrogates. Each is transmitted to PostgreSQL as a separate text value, whose UTF-8 encoding replaces it with U+FFFD; joining the stored text chunks cannot reconstruct the original character. This silently corrupts known words, decisions, snapshots, queues, and complete backups, despite a successful save/restore. Keep chunk boundaries outside surrogate pairs or stage an encoding that preserves the original bytes.

Confirmed through the real remote adapter and PGlite. Run this from the project root with `node --import tsx --input-type=module` on stdin:

```js
import { PGlite } from '@electric-sql/pglite';
import { drizzle } from 'drizzle-orm/pglite';
import { readFile } from 'node:fs/promises';
import { createPostgresStore } from './src/server/store.ts';
import { createRemoteAppStore } from './src/storage/remote-store.ts';
const pg = new PGlite();
await pg.exec(await readFile('migrations/0000_postgres_store.sql', 'utf8'));
const dispatch = createPostgresStore(drizzle(pg));
const store = createRemoteAppStore({ fetch: async (_u, init) => {
  try { return Response.json(await dispatch(JSON.parse(init.body))); }
  catch (e) { return Response.json({ error: e.message, code: e.code }, { status: e.status ?? 500 }); }
}});
const prefix = JSON.stringify({ id: 'known', name: '', words: [] }).indexOf('"name":"') + 8;
const name = 'a'.repeat(59999 - prefix) + '😀';
await store.knownWords.save('known', name, ['猫']);
const restored = await store.knownWords.getActive();
console.log({ same: restored.name === name, originalTail: name.slice(-8), restoredTail: restored.name.slice(-8) });
await pg.close();
```

Observed: `{ same: false, originalTail: 'aaaaaa😀', restoredTail: 'aaaaaa��' }`.

### P2 — Prevent old UI mutations from running after a complete restore

Location: `src/components/study-runtime.ts:78–80`; serialization in `src/storage/remote-store.ts:35–39`.

Version 3 restore directly calls the remote store while the controller and its controls remain active. A decision, queue, or preference operation submitted during a long restore is queued behind it. Once restore completes, that captured old UI operation automatically receives the newly acknowledged revision and can alter the restored state. Requesting navigation afterward does not cancel a request already accepted by the server; a navigation prevented by the new pending-write unload protection leaves the stale controller live as well. Freeze/cancel mutations and outstanding controller work during restore, and keep the old controller disabled after commit until reinitialization/navigation succeeds.

Adapter-level reproduction using the setup above: export an empty backup; call `store.restoreCompleteBackup(backup)` and, without awaiting it, call `store.wordDecisions.set({ normalizedWord: 'old-ui-word', status: 'known', updatedAt: '2026-09-14' })`; await both. The resulting database contains `old-ui-word` even though the restored backup has no decisions. This confirms the queue ordering; the browser navigation race itself was not separately exercised.

### P2 — Do not report successful export for a backup the app cannot restore

Location: `src/storage/remote-store.ts:185–197`.

The application can retain multiple datasets, each accepted up to 256 MiB, but complete export aggregates all of them without enforcing a size limit and emits indented JSON. Restore rejects the entire uploaded file above 256 MiB before parsing it, and the compact state upload has the same aggregate cap. Thus ordinary accumulation of individually valid datasets can produce an exported file that cannot be restored. Indentation can also push an otherwise admissible compact payload over the initial text-size check. Align the export/restore limits or provide a bounded backup format supporting all saved application data; at minimum fail export visibly before claiming it is a usable backup.

## Resolution review — 2026-09-14

All three reported findings are resolved in the current implementation. The earlier findings above are retained as the historical review record; this resolution supersedes the prior failing assessment.

- **Unicode preservation:** staged text chunks move their boundary backward when it would separate a high/low surrogate pair. Regression cases for both emoji and supplementary Japanese `𠮷` cross the original failing boundary and preserve the saved value.
- **Restore lifecycle:** complete restore now passes through the controller's import/user-state locks and invalidates old imports, user-state epochs, queries, review, and coverage. A final epoch increment drops decisions/preferences submitted during replacement. The runtime disposes event bindings, practice interactions, and pending search work before restoring and marks the study surface inert; it remains frozen if navigation or confirmation fails. Existing synchronous queue submissions enter the remote queue before restore; the frozen UI prevents new queue submissions during restore.
- **Restorable export:** complete export measures the final indented JSON in UTF-8 against the same 256 MiB limit used by restore and raises a visible export error instead of returning an unusable file. The aggregate backup limit remains an explicit functional limit; backups above it are not supported.

Focused verification: `npx vitest run tests/server/postgres-store.test.ts tests/app/complete-restore.test.ts -t 'preserves|rejects complete exports|drops old decisions'` completed successfully: **4 passed, 13 skipped**, across two files. These tests use isolated PGlite/memory stores. No browser tests or shared PostgreSQL operations were run during re-review.

**Assessment:** targeted quality/spec review passes for the three findings. No remaining actionable issue identified within this re-review scope.
