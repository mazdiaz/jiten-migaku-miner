# Scalable Local-First Miner Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Split the static Jiten/Migaku miner into a tested, worker-backed, local-first TypeScript application that preserves current workflows while supporting datasets up to 100,000 rows and future remote adapters.

**Architecture:** Keep domain logic pure and framework-free. Run import and query work in a Web Worker, persist versioned data through IndexedDB ports, and keep DOM/Migaku behavior inside UI adapters. Use a staged rollout so the existing HTML launcher remains usable until the replacement passes browser checks.

**Tech Stack:** TypeScript with strict checking, Vite, Vitest, Playwright, `happy-dom` for DOM unit tests, native Web Workers, native IndexedDB, and `fake-indexeddb` for repository tests.

**Spec:** `docs/superpowers/specs/2026-09-04-scalable-local-first-architecture-design.md`

## Global Constraints

- Preserve current importer, filters, highlighting, pagination, auto-loading, and persistence behavior.
- Keep runtime deployment static and local-first.
- The app remains framework-free at first.
- Domain functions receive values and return values.
- Worker never updates IndexedDB directly; persistence remains an app/storage responsibility.
- Local data never leaves the browser by default.
- A malformed replacement import cannot remove or replace a working dataset.
- A 100,000-row import must not create 100,000 DOM nodes.
- `index.html` is canonical; `jiten-migaku-miner-v1.html` remains a compatibility entry point.
- Do not commit changes unless the user explicitly requests a commit.

```ts
type WorkerRequest =
  | { protocolVersion: 1; type: "import-jiten"; requestId: string; name: string; text: string }
  | { protocolVersion: 1; type: "import-known"; requestId: string; name: string; text: string }
  | { protocolVersion: 1; type: "load-start"; requestId: string; datasetId: string }
  | { protocolVersion: 1; type: "load-chunk"; requestId: string; datasetId: string; chunkIndex: number; entries: Entry[] }
  | { protocolVersion: 1; type: "load-complete"; requestId: string; datasetId: string }
  | { protocolVersion: 1; type: "query"; requestId: string; datasetId: string; knownWords: string[]; query: QueryState; window?: QueryWindow }
  | { protocolVersion: 1; type: "cancel"; requestId: string }
  | { protocolVersion: 1; type: "dispose"; requestId: string };

type QueryRequest = Extract<WorkerRequest, { type: "query" }>;
```

Responses must include `protocolVersion`, `type`, and `requestId`. Import emits bounded `import-chunk` messages followed by `import-complete`; query emits `query-result`; all failures emit `error` with `code` and `message`.
